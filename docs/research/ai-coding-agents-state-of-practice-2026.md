# AI Coding Agents on Real Codebases — State of Practice Brief (2025–2026)

**Method & confidence caveat.** This was built from search-result mining only (no page fetches). Titles, abstracts and headline summaries were triangulated across multiple sources; where I could not see a full paper or a full methods section, I say so. Treat every number below as "reported by the cited source", not independently reproduced. arXiv IDs are cited in canonical `arxiv.org/abs/<id>` form; several were surfaced via mirrors (ar5iv, scirate, HuggingFace papers).

## 1. Spec-driven development (SDD)

- **Spec Kit's chain is: `constitution → specify → clarify → plan → tasks → analyze → implement`**, exposed as slash commands after `specify init`; `clarify` and `analyze` are the later additions and are the parts most teams skip ([spec-kit README](https://github.com/github/spec-kit/blob/main/README.md?plain=1), [Spec Kit docs: Agentic SDD](https://github.github.com/spec-kit/reference/agentic-sdd.html)).
- **Kiro's chain is narrower and file-based**: `requirements.md` in EARS form → `design.md` → `tasks.md`, plus persistent *steering files* and event-triggered *hooks* — i.e. AWS ships enforcement (hooks) alongside the artifacts, which Spec Kit does not ([Kiro specs steering](https://github.com/cremich/promptz.lib/blob/main/steering/kiro-specs.md), [SD Times](https://sdtimes.com/ai/amazon-launches-spec-driven-ai-ide-kiro/)).
- **Tessl goes furthest: spec-as-source**, where the spec is the artifact of record and code is regenerated from it. This is the most aggressive and least evidenced position ([Tessl docs](https://docs.tessl.io/use/spec-driven-development-with-tessl.md), [comparison](https://particula.tech/blog/spec-driven-development-tools-spec-kit-vs-kiro-vs-tessl), [skeptical review](https://codemyspec.com/blog/tessl-review)).
- **Evidence for benefit is weak and mostly practitioner-anecdotal.** Thoughtworks treats SDD as a 2025 practice worth *assessing*, not adopting wholesale ([Thoughtworks](https://www.thoughtworks.com/en-us/insights/blog/agile-engineering-practices/spec-driven-development-unpacking-2025-new-engineering-practices), [Radar](https://www.thoughtworks.com/zh-cn/radar/languages-and-frameworks/github-spec-kit)). The widely-circulated "human-refined specs cut LLM code errors ~50%" and "5 people/7 days vs 20 people/weeks" figures trace to vendor/press retellings, not a controlled study ([Aliyun writeup](https://developer.aliyun.com/article/1734572)). **Treat as marketing.**
- **The measured failure modes are documented in the tool's own issue tracker**: Spec Kit "creates the illusion of work, generating a bunch of text" ([issue #75](https://github.com/github/spec-kit/issues/75)); tasks execute without adequate human oversight ([issue #385](https://github.com/github/spec-kit/issues/385)); generated documents carry high maintenance cost ([issue](https://github.com/sohei56/claude-scrum-team/issues/6)).
- **Two structural critiques recur**: SDD collapses into waterfall when specs are written once up-front ([marmelab](https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html), [dev.to](https://dev.to/pacheco/spec-driven-development-isnt-waterfall-but-it-keeps-ending-up-there-4eei)), and it has a **blind spot at the seams** — specs describe components, not the integration surfaces where agents actually break systems ([HackerNoon](http://hackernoon.com/spec-driven-development-has-a-blind-spot-the-seams)).
- **The field's own correction**: Spec Kit users are asking that constitution principles *compile to executable architecture tests (fitness functions)* rather than being LLM-reviewed ([spec-kit discussion #3674](https://github.com/github/spec-kit/discussions/3674)).

**So what:** make the constitution *compile* — every principle must emit a machine check id, or it is decoration.
**Disagreement/evidence:** all pro-SDD numbers I found are anecdotal or vendor-sourced; the failure-mode evidence is first-party and concrete. That asymmetry is the finding.

## 2. Context engineering

- **The canonical taxonomy is write / select / compress / isolate** (LangChain), now the default vocabulary ([LangChain](https://www.langchain.com/blog/context-engineering-for-agents)).
- **Anthropic's framing is "finite attention budget": find the smallest set of high-signal tokens**, with just-in-time retrieval, compaction, structured note-taking and sub-agent isolation as the mechanisms ([Anthropic cookbook](https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools), [eWeek summary](https://www.eweek.com/news/anthropic-context-engineering-building-ai-workflows/)).
- **Context rot is measured, not folklore.** Chroma tested 18 models and found performance degrades non-uniformly as input grows, with distractors — not length alone — driving failure ([Chroma research](https://www.trychroma.com/research/context-rot), [ZenML writeup](https://www.zenml.io/llmops-database/context-rot-evaluating-llm-performance-degradation-with-increasing-input-tokens)). **LOCA-bench** (ICML 2026) extends this to agents under controlled extreme context growth ([ICML](https://icml.cc/virtual/2026/poster/64486), [paper](https://huggingface.co/papers/2602.07962)).
- **Manus's decisive factor is KV-cache hit rate**, achieved by append-only context and stable prompt prefixes, plus using the *file system as context* rather than stuffing the window ([Manus](https://manus.im/en/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus), [ZenML](https://www.zenml.io/llmops-database/context-engineering-strategies-for-production-ai-agents)).
- **Spotify's reported decisive factor is tool design, not prompt text** — context engineering and tool surface for *background* coding agents at scale, now productised as the Xirp harness across ~1,300 engineers running Claude/Codex/Gemini ([ZenML/Spotify](https://www.zenml.io/llmops-database/context-engineering-and-tool-design-for-background-coding-agents-at-scale), [Spotify Engineering](https://engineering.atspotify.com/2026/6/code-with-claude-coding-is-no-longer-the-constraint), [Xirp coverage](https://betterstack.com/community/guides/ai/xirp-agent/)).
- **Cognition publicly reversed position.** "Don't Build Multi-Agents" (context fragmentation, conflicting decisions) was followed by "Multi-Agents: What's Actually Working" — the reconciliation is that isolation works for *read-heavy, decision-light* subtasks and fails for shared-decision work ([Cognition 1](https://cognition.com/blog/dont-build-multi-agents), [Cognition 2](https://cognition.com/blog/multi-agents-working), [ZenML](http://www.zenml.io/llmops-database/multi-agent-systems-in-production-code-generation-and-review-at-scale)).
- **Isolation is not free**: Anthropic's own multi-agent research system reports roughly an order-of-magnitude token multiplier over single-agent chat ([Simon Willison](https://simonwillison.net/2025/Jun/14/multi-agent-research-system/), [ZenML](https://www.zenml.io/llmops-database/building-production-multi-agent-research-systems-with-claude)).

**So what:** budget context as a *hard resource* — cap injected tokens per turn, retrieve just-in-time via file paths, and isolate only read-heavy subtasks.
**Disagreement:** LangChain/Anthropic favour aggressive sub-agent isolation; Cognition's first post argues the opposite. Both are experience reports, not benchmarks. Chroma and LOCA-bench are the only *measured* items here.

## 3. AGENTS.md

- **Adoption is real and now institutional**: ~60,000 repositories, and the spec has moved under the Linux Foundation's Agentic AI Foundation alongside MCP ([agentmarketcap](https://agentmarketcap.ai/blog/2026/04/17/agents-md-60k-adoption-aaif-donation-standards-floor), [Digital Watch](https://dig.watch/updates/openai-launches-agentic-ai-foundation-with-industry-partners), [OSFY](https://www.opensourceforu.com/2025/12/anthropic-openai-block-move-agentic-ai-infrastructure-to-open-source-governance-under-linux-foundation/)).
- **Two independent studies find the effect is far smaller than assumed.** `Evaluating AGENTS.md` (arXiv 2602.11988, Gloaguen & Mündler) and `Do Context Files Help Coding Agents? A Two-Agent Ablation Study` (arXiv 2607.27250) both report no reliable improvement in task resolution from adding context files ([2602.11988](https://arxiv.org/abs/2602.11988), [2607.27250](https://arxiv.org/html/2607.27250v1), [The Agent Times](https://www.theagenttimes.com/articles/study-finds-agents-md-and-claude-md-files-do-not-improve-cod-4f4d49e7), [InfoQ](https://www.infoq.com/news/2026/03/agents-context-file-value-review/)).
- **Length actively hurts.** The consistent read of the research is "your AGENTS.md is probably too long"; heise frames it as *briefing or token hog* ([Upsun](https://developer.upsun.com/posts/ai/agents-md-less-is-more), [heise](https://www.heise.de/en/background/AGENTS-md-Helpful-agent-briefing-or-token-hog-11245317.html)). A 138-repo analysis reaches the same conclusion ([dev.to](https://dev.to/umesh_malik/agentsmd-files-dont-work-the-way-you-think-a-138-repo-study-proves-it-2k1g)).
- **The structural recommendation that survives is: AGENTS.md as a table of contents, not an encyclopedia** — an index pointing to layered, scope-local files loaded on demand ([AgentPatterns](https://www.agentpatterns.ai/instructions/agents-md-as-table-of-contents/), [layered scopes](https://agentpatterns.ai/instructions/layered-instruction-scopes/), [why one giant file fails](https://walkinglabs.github.io/learn-harness-engineering/en/lectures/lecture-04-why-one-giant-instruction-file-fails/)).
- **Concrete token budgets are being enforced in the wild**: vLLM documents a "token budget mindset" for agent instructions; projects file issues when AGENTS.md exceeds ~6.6KB ([vLLM](https://verl.readthedocs.io/en/latest/contributing/editing-agent-instructions.html), [issue #1335](https://github.com/rjmurillo/ai-agents/issues/1335)).
- **Known failure modes**: silently ignored beyond a rule-count ceiling, stale relative to code, and duplicated across nine per-IDE formats ([instruction compliance ceiling](https://agentpatterns.ai/instructions/instruction-compliance-ceiling/), [empirical baseline](https://github.com/agentpatterns-ai/website/blob/main/instructions/empirical-baseline-agentic-config.md), [AIware 2026 exploratory study](https://2026.aiwareconf.org/details/aiware-2026-papers/2/)).

**So what:** cap the root AGENTS.md hard (index only), push detail into per-module files loaded on touch, and lint for size + staleness.
**Disagreement:** the *pro* case ("don't ditch AGENTS.md, fix what's in it", [dev.to](https://dev.to/dortort/dont-ditch-agentsmd-fix-whats-in-it-24ph)) is anecdotal; the *null-result* case is peer-reviewed-track and replicated twice. Weight accordingly.

## 4. Guardrails vs guidance

- **The core paper is `Guardrails Beat Guidance: A Large-Scale Study of Rules, Skills, and Persistent Configuration for Coding Agents` (arXiv 2604.11088)**, also titled *Do Agent Rules Shape or Distort?* — the second title is the important one: rules do not merely under-perform, they can **distort** behaviour ([arXiv 2604.11088](https://arxiv.org/abs/2604.11088), [scirate](https://scirate.com/arxiv/2604.11088), [analysis](https://arxivlens.com/paperview/details/do-agent-rules-shape-or-distort-guardrails-beat-guidance-in-coding-agents-7861-67c2a8c7)).
- **The practitioner formulation**: hooks for enforcement, prompts for guidance — a prompt is a probability, a hook is a gate ([source doc you referenced](https://github.com/agentpatterns-ai/website/blob/main/instructions/guardrails-beat-guidance-coding-agents.md), [hooks vs prompts](https://github.com/agentpatterns-ai/website/blob/main/instructions/hooks-vs-prompts.md), [deterministic guardrails](https://agentpatterns.ai/verification/deterministic-guardrails/)).
- **The sharpest concrete claim: restraint rules ("never do X") need external enforcement** — prohibitions degrade fastest under context pressure, because compliance competes with task pressure ([AgentPatterns](https://agentpatterns.ai/instructions/restraint-rules-need-external-enforcement/)). Corollary: prefer positive/actionable phrasing ([instruction polarity](https://github.com/agentpatterns-ai/website/blob/main/instructions/instruction-polarity.md)).
- **There is a rule-count ceiling**: compliance falls as rule count rises, so adding a rule to fix a failure can lower compliance with existing rules ([instruction compliance ceiling](https://agentpatterns.ai/instructions/instruction-compliance-ceiling/)). Practitioner reports circulate a ~70% compliance wall ([analysis](https://hatohato.jp/blog/core/single.php?id=590)) — **treat that specific number as anecdotal**.
- **Security reinforces the same conclusion**: "the model is not the firewall" — policy must sit outside the model ([AgentPatterns security](https://learn.agentpatterns.ai/security/the-model-is-not-the-firewall/)).

**So what:** for every rule you can express, either bind it to a blocking check or delete it — an unenforced rule costs tokens and lowers compliance with the enforced ones.
**Disagreement:** I could not verify the paper's effect sizes from snippets. The *direction* is corroborated by the AGENTS.md null results (§3); the *magnitude* is unverified.

## 5. Verification & evaluation loops

- **The strongest measured result in this brief: SWE-Review.** An agentic review loop lifted Qwen3-30B from **27.5% → 56.9% on SWE-bench Verified**, at **6.5× better token efficiency than independent resampling** ([arXiv 2607.06065](https://arxiv.org/abs/2607.06065), [repo](https://github.com/SWE-Lego/SWE-Review), [summary](https://aiweekly.co/node/5865)). That is review-as-feedback beating brute-force best-of-n.
- **Adversarial review beats consensus review.** *Adversarial Review: Structured Disagreement for Grounded Agentic Code Review* reports 3 structured-disagreement agents outperforming 5-agent consensus systems — more agents ≠ better ([arXiv 2608.18167](https://arxiv.org/abs/2608.18167), [writeup](https://codex.danielvaughan.com/2026/08/20/adversarial-review-structured-disagreement-false-consensus-codex-cli-guardian-multi-agent-code-review/)).
- **Self-consistency for patches is an old, real result** (Majority Rule: better patching via self-consistency) and remains the cheap baseline that test-time scaling must beat ([arXiv 2306.00108](https://arxiv.org/abs/2306.00108)).
- **But the reward signal itself is the limiting factor.** *The Verification Horizon: No Silver Bullet for Coding Agent Rewards* argues verification signals saturate — tests pass while the change is wrong ([arXiv 2606.26300](https://arxiv.org/abs/2606.26300)). Independent patch verification is being proposed as a separate stage ([arXiv 2608.08950](https://arxiv.org/html/2608.08950v1)).
- **Benchmark numbers are contaminated.** *The SWE-Bench Illusion* shows SOTA models partly memorise rather than reason ([arXiv 2506.12286](https://arxiv.org/abs/2506.12286), [ACM](https://dl.acm.org/doi/10.1145/3786583.3786882)); OpenAI itself called the benchmark contaminated ([coverage](https://tech.yahoo.com/ai/chatgpt/articles/openai-says-benchmark-used-measure-213029876.html)). Two vendors simultaneously claimed **#1** on it ([Sonar PR](https://www.sonarsource.com/company/press-releases/sonar-claims-top-spot-on-swe-bench-leaderboard/), [two #1s](https://agentmarketcap.ai/blog/2026/04/18/sonar-vs-claude-opus-swe-bench-two-number-ones)).
- **Org-level data says review is now the bottleneck**: AI-assisted PRs merge at roughly *half* the rate of human-authored ones, and tripled PR output did not reduce total dev time ([LinearB 2026](https://linearb.io/dev-interrupted/podcast/linearb-2026-benchmarks-ai-pr-merge-rate), [Developers Digest](https://www.developersdigest.tech/blog/coding-agents-tripled-prs-linear-data-2026)). METR's RCT found experienced devs **19% slower** with AI tools ([METR](https://tagteam.harvard.edu/hub_feeds/1834/feed_items/14760086), [InfoWorld](https://www.infoworld.com/article/4020931/ai-coding-tools-can-slow-down-seasoned-developers-by-19.html)).

**So what:** put a *structured-disagreement review gate* between patch and merge, and spend test-time compute on review rather than on resampling.
**Disagreement:** vendor SWE-bench claims vs contamination findings are in open conflict. LinearB/METR (measured, org-level) contradict vendor throughput claims; Microsoft reports +24% PRs ([study](https://lumienai.com/news/microsoft-ai-coding-agents-pull-requests-24-percent-study)) — but PR count is not delivery.

## 6. Architecture governance

- **The classic material has been re-issued for the agent era**: Ford & Richards' *Architecture as Code* and O'Reilly's *How Agentic AI Empowers Architecture Governance* both push fitness functions from "nice practice" to "the interface agents must respect" ([O'Reilly Radar](https://www.oreilly.com/radar/how-agentic-ai-empowers-architecture-governance/), [Architecture as Code](https://bookshop.org/p/books/architecture-as-code-understanding-qualitative-trade-offs-mark-richards/7ae1f7a710e6267c)).
- **The genuinely new idea is that agents make fitness functions a team discipline** rather than an architect's side-project, because the agent will violate any boundary that isn't executable ([LavX](https://news.lavx.hu/article/ai-makes-evolutionary-architecture-a-team-discipline)).
- **ArchUnit-style enforcement is being wired directly into agent loops** — package-boundary rules enforced on agent output rather than in review ([dev.to](https://dev.to/machinecodingmaster/stop-fixing-broken-architecture-auto-enforce-package-boundaries-with-cursor-composer-and-archunit-279l)).
- **Drift detection has become a tool category**: purpose-built "catch architectural drift for agentic coding" tooling now exists ([unkode](https://github.com/deepcodersinc/unkode), [archtest](https://www.npmjs.com/package/@rickheere/archtest), [architecture-guard](https://github.com/DyanGalih/architecture-guard)).
- **ADR practice has two live extensions**: git-native ADRs as *enforceable shared context* for agents ([decider](https://github.com/sventorben/decider)) and **Agent Decision Records (AgDR)** — a separate record type for decisions the *agent* made ([AgDR](https://github.com/me2resh/agent-decision-record)). Mainstream repos are formally adopting ADRs specifically for agent legibility ([vercel/ai ADR-0001, 2026-03](https://github.com/vercel/ai/blob/429b88a7/contributing/decisions/2026-03-11-adopt-architecture-decision-records.md)).

**So what:** every ADR needs an `Enforced-by` pointer to a real check, and agent-made decisions need their own record type so they don't masquerade as human intent.
**Disagreement:** none substantive; but **all of this is prescription, not measurement** — I found no study measuring whether fitness functions reduce agent-induced drift.

## 7. Multi-repo / microservices + agents

- **"One agent per repo" is an articulated orchestration pattern**, motivated by context limits: one repo small enough that one agent holds its whole model ([dev.to](https://dev.to/just_an_electron/one-agent-per-repo-an-orchestration-pattern-for-multi-repo-ai-coding-49ba), [multi-repo as coordination problem](https://dev.to/ramcsamal/multi-repo-microservice-changes-are-a-coordination-problem-i-solved-it-with-ai-agent-teams-34mf)).
- **The counter-position is loud**: monorepo + full-stack is argued to have gone from "outdated" to "default" precisely *because* agents need one coherent tree ([Aliyun](https://developer.aliyun.com/article/1748910)). This is a live, unresolved split.
- **Contract testing is the named mitigation.** Pact remains active with bi-directional contract testing, and agent-authored specs are being validated through consumer-driven contracts ([Pact OSS update May 2026](https://docs.pact.io/blog/2026/05/22/pact-open-source-update-may-2026), [agent-authored specs](https://www.augmentcode.com/guides/api-contract-testing-agent-authored-specs), [Codex CLI + PactFlow MCP](https://codex.danielvaughan.com/2026/05/17/codex-cli-contract-testing-pactflow-mcp-consumer-driven-verification/)). LLM-based impact reasoning on contracts is an early research thread ([IJISAE](https://mail.ijisae.org/index.php/IJISAE/article/view/8320)).
- **API versioning has a new requirement: machine-parseable change communication.** Semver alone is insufficient when the consumer is an agent; changelogs must be structured ([rhumb.dev](https://rhumb.dev/blog/machine-parseable-change-communication-for-agent-ready-apis), [API Evangelist](https://papers.apievangelist.com/papers/change-on-the-agent-surface/), [tool schemas as API contracts](https://dev.to/james_oconnor_dev/we-version-our-tool-schemas-like-an-api-contract-because-the-agent-is-a-consumer-43fc)).
- **Yes — co-change analysis is being used for boundary placement, and its limits are being reported.** Repowise ships git co-change intelligence for multi-repo system maps ([docs](https://docs.repowise.dev/docs/intelligence/git-history), [system map](https://docs.repowise.dev/docs/multi-repo/system-map)) *and* published a post-mortem on their co-change model failing on a monorepo refactor ([repowise](https://www.repowise.dev/blog/engineering/our-git-co-change-model-failed-on-a-monorepo-refactor)). The academic base is solid and predates agents ([co-change patterns, a large-scale empirical study, JSS](https://www.sciencedirect.com/science/article/abs/pii/S0164121219300597); the classic *The Link between Dependency and Cochange* IEEE TSE 2011, doi:10.1109/TSE.2011.91).

**So what:** treat cross-repo contracts as the governed surface (versioned, sunset-dated, impact-costed), and use co-change as a *signal* for boundary review — with a known false-positive mode on large refactors.
**Disagreement:** repo-per-service vs monorepo is genuinely contested; both sides argue from agent context limits and reach opposite conclusions. No measurement either way.

## 8. Memory / long-horizon agents

- **Compaction is the dominant failure mode, and it has a name and a paper**: *The Compaction Cliff in Long-Running AI Agent Memory* ([arXiv 2608.22752](https://arxiv.org/abs/2608.22752)) — quality does not degrade gracefully, it falls off.
- **Compaction does not fix drift.** ContextEcho benchmarked persona/instruction drift across **23 models** in long agentic-coding sessions and reports that compaction does *not* correct drift ([arXiv 2605.24279](https://arxiv.org/abs/2605.24279), [ActuIA](https://www.actuia.com/en/news/contextecho-compaction-does-not-correct-persona-drift-benchmark-on-23-models/)). This is the single most under-appreciated finding for scaffold builders: your constitution decays *within* a session.
- **Files beat vector stores for agent working memory in most reported cases.** Manus uses the filesystem as externalised context ([Manus](https://manus.im/en/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)); Oracle's comparison and practitioner reports converge on flat files for state and databases only for genuine recall at scale ([Oracle](https://blogs.oracle.com/developers/comparing-file-systems-and-databases-for-effective-ai-agent-memory-management), [dev.to](https://dev.to/manja316/when-does-flat-file-memory-beat-a-vector-db-for-your-agent-4bnd)).
- **Memory should be treated as a lifecycle/architecture problem, not a storage choice** — explicit write/promote/evict stages with cost accounting ([Agentic Context Management, arXiv 2607.21503](https://arxiv.org/abs/2607.21503); rate-distortion framing of what to keep vs forget, [arXiv 2607.08032](https://scirate.com/arxiv/2607.08032)).
- **Real harnesses ship compaction bugs**: empty fallback summaries, premature compaction from miscounted cache-read tokens, and short-session patterns that never compact at all ([openclaw #72964](https://github.com/openclaw/openclaw/issues/72964), [#60719](https://github.com/openclaw/openclaw/issues/60719)). Three named failure modes and an "enforcement floor" are catalogued in ([IdeaBosque](https://www.ideabosque.com/library/agent-memory-design-patterns-persistent-context/)).

**So what:** persist state as committed files with a bounded, *derived* recap command — never rely on a compaction summary as ground truth, and re-inject invariants periodically because drift is not self-correcting.
**Disagreement:** vendor "agent memory" products claim vector recall is essential; the measured papers point at compaction/lifecycle, not retrieval, as the failure. Files-vs-vector is largely anecdotal on both sides.

## 9. Things you didn't ask about that matter

- **Instruction files are now an attack surface.** CSA documents README/instruction injection hijacking coding assistants ([CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-readme-instruction-injection-ai-coding-age/), [TrapDoor supply-chain](https://labs.cloudsecurityalliance.org/research/csa-research-note-trapdoor-multi-ecosystem-supply-chain-ai-t/)). Mitiga found **1,230+ leaking API keys** and attacker-controlled `ANTHROPIC_BASE_URL` overrides inside AI instruction files ([Mitiga](https://www.mitiga.io/blog/malware-in-ai-instruction-files-skillgate), [CSO](https://www.csoonline.com/article/4204731/attackers-are-crafting-malicious-ai-instruction-files-to-turn-your-agentic-workflows-into-quiet-criminal-helpers.html)). Detection tooling for malicious rule files exists ([ide-rule-detector](https://github.com/spiffy-oss/ide-rule-detector)). **Your AGENTS.md and skills are executable-adjacent inputs — scan them.**
- **Skills (progressive disclosure) have largely displaced long prompts** as the distribution unit for procedure: metadata loaded always, body loaded on demand ([Strapi](https://strapi.io/blog/what-are-agent-skills-and-how-to-use-them), [DeepWiki](https://deepwiki.com/wshobson/agents/2.3-skills-and-progressive-disclosure)). Adoption is large enough to be a marketplace ([coverage](https://agentskillexchange.com/claude-code-skill-system-changed-everything/)).
- **Standards consolidated fast**: AGENTS.md + MCP under the Linux Foundation's Agentic AI Foundation, backed by OpenAI, Anthropic and Block ([Digital Watch](https://dig.watch/updates/openai-launches-agentic-ai-foundation-with-industry-partners)). Betting on proprietary per-IDE rule formats is now a losing position.
- **Multi-agent scaling has diminishing returns**, reported repeatedly: agent count past ~3 yields worse repository-level outcomes than structured disagreement among fewer ([Adversarial Review](https://arxiv.org/abs/2608.18167), [orchestration cost](https://coasty.ai/blog/multi-agent-orchestration-patterns-computer-use-20260407)).
- **The "audit tax" is the emerging org-level cost**: throughput gains are consumed by verification ([AI Weekly](https://aiweekly.co/alerts/for-coding-agents-verification-is-now-the-harder-problem), [productivity-reliability paradox](https://www.openmercato.com/blog-posts/productivity-reliability-paradox)).

## TOP 10 THINGS A 2026 SCAFFOLD SHOULD HAVE

1. **A structured-disagreement review gate between patch and merge** — the only large measured win in the field (27.5%→56.9%, 6.5× token efficiency) ([SWE-Review](https://arxiv.org/abs/2607.06065); [Adversarial Review](https://arxiv.org/abs/2608.18167)).
2. **Every rule bound to a blocking deterministic check, or deleted** — unenforced rules both fail and degrade compliance with enforced ones ([2604.11088](https://arxiv.org/abs/2604.11088); [restraint rules](https://agentpatterns.ai/instructions/restraint-rules-need-external-enforcement/)).
3. **A hard token budget on always-loaded instructions, with AGENTS.md as an index only** — two studies find long context files don't help and cost tokens ([2602.11988](https://arxiv.org/abs/2602.11988); [2607.27250](https://arxiv.org/html/2607.27250v1); [table-of-contents pattern](https://www.agentpatterns.ai/instructions/agents-md-as-table-of-contents/)).
4. **Constitution principles that compile to executable fitness functions**, not LLM-reviewed prose ([spec-kit #3674](https://github.com/github/spec-kit/discussions/3674); [O'Reilly](https://www.oreilly.com/radar/how-agentic-ai-empowers-architecture-governance/)).
5. **Periodic re-injection of invariants mid-session**, because compaction demonstrably does not correct drift across 23 models ([ContextEcho](https://arxiv.org/abs/2605.24279); [Compaction Cliff](https://arxiv.org/abs/2608.22752)).
6. **Committed file-based memory with a bounded derived recap command** — never trust a compaction summary as project state ([Agentic Context Management](https://arxiv.org/abs/2607.21503); [Manus](https://manus.im/en/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)).
7. **Just-in-time retrieval by path with a per-turn context cap**, because degradation is driven by distractors, not just length ([Chroma](https://www.trychroma.com/research/context-rot); [LOCA-bench](https://icml.cc/virtual/2026/poster/64486)).
8. **Sub-agent isolation restricted to read-heavy, decision-light work**, with an explicit token-multiplier budget ([Cognition](https://cognition.com/blog/multi-agents-working); [Anthropic multi-agent](https://simonwillison.net/2025/Jun/14/multi-agent-research-system/)).
9. **Versioned, sunset-dated cross-repo contracts with machine-parseable change communication and consumer-driven contract tests** ([Pact 2026](https://docs.pact.io/blog/2026/05/22/pact-open-source-update-may-2026); [rhumb.dev](https://rhumb.dev/blog/machine-parseable-change-communication-for-agent-ready-apis)).
10. **A security scan of your own instruction/skill files as untrusted input** — injection and credential leakage through AGENTS.md/SKILL.md is measured and active ([Mitiga](https://www.mitiga.io/blog/malware-in-ai-instruction-files-skillgate); [CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-readme-instruction-injection-ai-coding-age/)).

---

**Biggest gap in the field:** governance prescriptions (fitness functions, ADRs, drift detection, SDD artifact chains) are almost entirely *unmeasured*. The only rigorously measured levers are review loops, context length effects, compaction failure, and the null result on context files. A 2026 scaffold should assume its governance layer is unproven and instrument it.
